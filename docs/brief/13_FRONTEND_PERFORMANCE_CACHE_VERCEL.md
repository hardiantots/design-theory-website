# 13_FRONTEND_PERFORMANCE_CACHE_VERCEL.md

## Scope

This project is frontend-only and deployed on Vercel.

Keep caching strategy simple.

Primary goal:

> New deployments should reliably show updated educational content without students being trapped on stale versions.

---

# Service Worker

For MVP:

## DO NOT IMPLEMENT A SERVICE WORKER.

Do NOT enable PWA caching unless there is a specific future requirement.

Reason:

Service workers can easily cause stale versions of:

- JS
- CSS
- theory content
- visual assets

to remain on student devices after deployment.

---

# Static Asset Strategy

Hashed build assets generated by the framework may use long-term immutable caching.

Example concept:

```txt
app.8f32ab.js
styles.abc918.css
```

These are safe because filename changes when content changes.

---

# Public Assets

Be careful with files such as:

```txt
/public/images/example.png
```

If frequently updated while keeping the same filename, browser/CDN cache may continue returning an older image.

Prefer versioned filenames:

```txt
hierarchy-example-v2.webp
```

rather than replacing:

```txt
hierarchy-example.webp
```

repeatedly.

---

# Theory Data

If theory content is bundled with the application:

```txt
src/content/*
```

it naturally receives a new build hash after deployment.

This is preferred.

Avoid dynamically fetching local JSON unless there is a specific reason.

---

# localStorage

localStorage is NOT application cache.

Use it only for:

```txt
bookmarks
progress
language
theme
playground
```

Never store core lesson content in localStorage.

---

# Version localStorage

Example:

```ts
const STORAGE_VERSION = 1
```

Possible structure:

```json
{
  "version": 1,
  "bookmarks": [],
  "progress": []
}
```

When a breaking schema update occurs:

```txt
detect old version
↓
migrate if easy
or
reset only affected local data
```

Never crash the application because old localStorage exists.

---

# Cache Busting

Do NOT manually add timestamp query strings everywhere.

Rely on framework asset hashing.

Use explicit asset versioning only where appropriate.

---

# Vercel

Inspect whether the repository contains:

```txt
vercel.json
next.config.*
vite.config.*
```

Do not add custom caching headers unless necessary.

Framework defaults are preferable for hashed assets.

---

# HTML

Avoid overly aggressive long-term browser caching for HTML entry pages.

New deployment HTML should be able to reference the newest asset hashes.

---

# Image Optimization

Prefer:

```txt
WebP
AVIF
SVG
```

where appropriate.

Use:

```txt
lazy loading
responsive sizes
appropriate dimensions
```

Avoid enormous images for simple theory diagrams.

---

# Animation Performance

Prefer:

```txt
transform
opacity
```

over repeated layout-affecting properties.

Avoid excessive:

```txt
box-shadow animation
filter blur animation
large DOM particle systems
```

---

# Bundle Size

Audit large dependencies.

Do not install a library for functionality easily implemented in a few lines.

Examples:

Avoid importing an entire charting library just to draw a simple Rule of Thirds grid.

SVG or CSS is sufficient.

---

# Lazy Loading

Lazy load heavier modules:

```txt
Playground
Color Lab
Complex Gestalt Animation
Teacher Presentation Mode
```

if the framework supports clean code splitting.

---

# Fonts

Avoid excessive font weights.

Example:

Instead of:

```txt
100
200
300
400
500
600
700
800
900
```

load only the weights actually used.

Prefer variable font where appropriate.

---

# Deployment Check

After each major change:

```txt
build locally
↓
check console errors
↓
check production build
↓
deploy preview
↓
verify mobile
↓
verify fresh refresh
↓
verify repeat visit
```

Check especially:

```txt
Chrome
Edge
Safari
Mobile browser
```

---

# Error Recovery

If localStorage parsing fails:

```ts
try {
  // load
} catch {
  // restore safe default
}
```

The application should still start.

---

# Main Rule

Keep the frontend predictable.

Do not introduce sophisticated caching infrastructure without a demonstrated problem.
